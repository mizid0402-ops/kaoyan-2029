## 1. 方法总述

1. 直接复用 `tools/round22_extract.py` 的 `extract_2022()` / `extract_2026()` 结构化抽取（章/节/条目三层），**不重新实现抽取**。
2. 写了一个**可重排（reorder-aware）、支持包含式回退（containment fallback）的通用对齐器** `align()`：
   - 第一遍：`difflib.SequenceMatcher` 在原文档顺序上找精确 key 相等的块（这是 round-22 已验证过的"两边都有"）；
   - 第二遍：**跨全部非 equal 区块**做一次全局精确 key 匹配（修复 `SequenceMatcher` 把纯换序拆成 insert+delete 导致漏配的问题——本报告第 9 节第 1 条记录了这个坑）；
   - 第三遍：包含式匹配（一个 key 是另一个的 ≥4 字子串，或 ≥2 字前缀——前缀规则专门覆盖 2022 抽取产物里"短标题后面直接拼接说明文字、无分隔符"的模式）；
   - 剩余的记为 `only_a`/`only_b`。
3. 对**自动对齐仍无法处理、但人工核对双方全文后可以确认是同一考点**的情况，维护了一份**显式、可审查的人工覆盖表**（章改名 2 条、节改名/合并 5 条、条目同义替换 11 条、拆分 3 条、跨节迁移 1 条、条目升格为节 1 条）——每条都在脚本里写明原因，本报告第 3/4 节完整列出。
4. 章/节/条目的 `knowledge_point_id` **直接复用现有 403 节点单源树**（`knowledge_tree.yaml`）的 ID 和 `title`（源 A 措辞），先验证了两边可以 100% 精确对应（214 个 2026 显式条目 key 与树里 214 个 `item-NN` 节点 key 完全双向对应，0 差集），再把 2022 的证据"贴"到已有节点上，而不是重新生成一套 ID。这保证了"加权树 ⊇ 单源树"是**逐 ID 可验证**的，不是靠标题模糊比对。
5. 2022 单边、且在自动+人工对齐后仍找不到对应的条目，作为**新节点**追加（7 个），ID 形如 `<父节 id>.legacy-item-NN`。

### 6.3 映射结论：无法映射，如实报告

`knowledgeTagsId` 是源库自己内部的数字 ID，**本机范围内没有任何文件能把这些数字解码成知识点名称**，因此**无法**建立"源 C 考点 id → 本树 `knowledge_point_id`"的对应关系。任务书要求的"树里有但从未考过的节点""源 C 有但树里没有的考点"这两项对照，**在当前证据下做不出来**——不是遗漏，是数据条件不满足。按任务书指示，如实说明，不强行拼凑。

## 11. 没有把握的地方

2. **`single_source_unverified` 与 `candidate_recent_new` 之间的边界是本轮设计决策，不是给定规则的直接产物**：任务书权重表里"2026 单边且疑似近年新增"和"仅一边出现且无任何支持"两档描述有重叠，本轮用"结构级新增（整章/整节）→ candidate_recent_new；结构未变、条目级单边→ single_source_unverified，明确点名的堆及其应用/多处理机调度除外"这条规则做区分，但这条区分规则本身未经任务书或 round-22 报告明确背书。

4. `knowledgeTagsId` 出现的 1 例逗号分隔多值 `"8,9"` 未做拆分统计（仍按原始字符串整体计数），如果源库里还有更多类似的多值记录被我漏检，`distinct_knowledge_tags_id=147` 这个数字可能需要修正；本轮只做了字符串级别的直接计数，没有对该字段做进一步的格式归一化。
