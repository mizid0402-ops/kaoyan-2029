## ① 对主控五个缺口的复核

### 缺口 1（当天状态快照缺失）—— **成立，且比主控描述的更缺一层**

实测：`longitudinal.py` 的 `DayPlan` 全部字段都是纯输入（dataclass frozen，无默认来源）；
`monthly_close.py` 的文档字符串明确写"reports, it does not prescribe"；
`ky/` 下不存在任何函数读取"各科还剩多少知识点/已学多少"。

推断（有依据）：这个数字**理论上可算**——`data/structured_materials/{math1,eng1,cs408}/knowledge_tree.yaml`
里的知识点 ID 与 `ReviewItem.knowledge_point_id`（见 `ky/models.py`）取差集，
就是"还没引入复习队列的知识点"。但**目前没有任何代码做这件事**，缺口成立。

**额外实测发现（主控未提及的风险点）**：三棵知识树的节点 `status` **全部是 `extracted`**
（math1 69 处、eng1 24 处、cs408 403 处，无一个 `approved`）。
`ky/knowledge/knowledge_point.py` 的 `NON_EXAMINABLE_SCOPES`/`STATISTICAL_VALIDATIONS`
机制以及 `math1/knowledge_tree.yaml` 文件头注释都明确写着：
**extracted 状态"不得用于频率统计、考纲覆盖率或能力画像"**。
"还剩多少/已学多少"这个统计，语义上非常接近"覆盖率"。
这不构成阻断②的理由（见下文判断），但状态快照模块**必须诚实标注数据来源的
approval 状态**，不能让"三科都还没审"的临时统计被当成权威覆盖率使用——这是一条
实施细节，我把它写进了③。

### 缺口 2（AI 提交决定的接口缺失）—— **成立**

实测：`DayPlan` 是纯 dataclass，无持久化方法；`ky/__main__.py` 只有 `preflight`
（只读，"Writes nothing"是文档明写的设计原则）和 `ledger`（同样只读）两个子命令；
全仓库搜索不到任何写入 `DayPlan`/`MonthClose` 的代码路径。

### 缺口 3（计划落盘与查询缺失）—— **成立，且与缺口 2 是同一个缺口的两面**

实测：`ky/storage/` 下只有 `review_shards.py`，其 `ReviewShardStore` 只认
`ReviewItem`（`validate_review_item`/`_item_mapping` 硬编码了 `ReviewItem` 的字段），
**结构上无法直接装 `DayPlan`**。缺口 2（写入口）和缺口 3（存哪/怎么查）本质是同一个
"日计划持久化模块"缺失，建议合并成一个实施单元处理，而不是两条独立任务
（见③、⑤）。

### 缺口 4（完成反馈回路缺失）—— **成立，而且比主控描述的更深一层**

实测：`monthly_close.py` 汇总的是传入的 `DayPlan` 列表本身（即"计划"），
没有任何字段区分"计划了多少"与"实际发生了多少"——`close_month` 的输入就是
`plans: list[DayPlan]`，没有第二个"实际"参数。

**更深一层（实测，主控未提到）**：我在 `ky/models.py` 和全仓库搜索了
"record/apply/complete/actual_minutes/last_quality 的写入路径"，
发现 `ReviewItem` 只有 `with_deferral()`（未完成时把 `defer_count+1`），
**没有任何函数在"今天真的复习完成"时推进 `due_date`/`interval_days`/
`ease_factor`/`repetitions`**（SM2/FSRS 式的"做对了就往后排"逻辑）。
也就是说，"月度闭环缺实际完成数据"不仅是②的问题——**间隔复习本身的
"完成后如何前进"这一步，在①阶段就没有实现**，②的闭环建立在一个本来就是空的地基上。
这件事值得单独向用户说清楚，但**不属于②的范围**（见⑥"明确不做"）。

### 缺口 5（系统/AI 边界未划清）—— **成立，是本轮最关键的一条，见④**

### 我新发现、主控五条里没有的第六个问题（实测，非主观外加）

`ky/schedule/review_clip.py::select_daily_reviews()` 的预算来源是
`total = config.total_daily_minutes`（`ky/models.py:254` 附近），
而 `KaoyanConfig.total_daily_minutes` 是**从配置文件加载一次的单一标量**
（`ky/models.py:315` 文档自称"the single authoritative daily budget"）。
换句话说：**复习通道（`review_clip.py`）目前完全不接受"当日 AI 自由给的分钟数"，
它的预算基准仍然是配置文件里那个写死的数**。

这不是我猜的——`docs/阶段2决议-预算与词汇编排.md` §3 的冲突清单里
**C6 条自己也写了**："硬上限仍需要，但其基准不再是 120"，"上限基准改为
'当日可用分钟 × 比例'"，并标注"落地时必须同步改"。也就是说这是决议文档
自己承认、但**主控的五个缺口里没有列出来**的一条已知未完成项。
如果不修，②哪怕把 `budget.py`/`longitudinal.py`/`vocab_channel.py` 全部接好，
复习通道依旧在用旧的固定预算跑——决议一（"120 不再写死"）对复习通道**实际上没有落地**。

**处置建议**：不替换 `review_clip.py` 的排序核（遵守纪律第 2 条），只给
`select_daily_reviews()` 加一个可选参数（如 `daily_minutes_override: int | None = None`，
缺省回退到 `config.total_daily_minutes` 保证向后兼容），硬上限/软配额基于这个值算。
这是"扩展签名"不是"替换算法"。

## ② 落地判断

**②能落地。不是"重新设计"，是"把已经写好、已经测过的五个纯函数模块接上持久化和一层薄 CLI"。**

理由：
- 五个核心计算模块（预算切分、复习排序、纵向护栏、词汇通道、月度汇总）**都已存在、
  都已通过实测的 306 个测试**，且都已经贯彻了"系统给护栏不给数值"的决议原则。
- 缺的东西（状态快照、持久化、CLI、边界规则）**都是胶水层和读写层**，

- 真正的"设计不确定性"只有一条：缺口 5 的边界怎么划——这条本方案在④给出可执行答案。

但落地判断有**一个前置性保留**，见 §7。

## ③ 最小可执行终态

**新增模块（3 个，全部是"胶水"，不碰已冻结的排序核）**：

1. `ky/schedule/state_snapshot.py`（新）
   - 纯函数：给定 `knowledge_tree` 路径集合 + 已加载的 `ReviewItem` 队列
     （复用 `ky/storage/review_shards.py::load_review_queue`）+ `vocab_channel.remaining_pool()`
     + horizon 起止日，算出一个 `StateSnapshot`：
     每科"知识树总条目数 / 已进入复习队列条目数 / 今日到期复习条数与分钟数 / 当前 backlog 分钟"、
     词汇通道"已投递词数 / 剩余词数"、"距考试天数"。
   - 每个来自知识树的数字必须**带 `tree_status` 字段**（如实反映 `extracted`/`approved`），
     不允许把未审核的计数伪装成权威覆盖率。
   - 只读，不写任何文件，不做任何"建议"。这是给 AI 看的"今天的仪表盘"，不是"今天该做什么"。

2. `ky/storage/day_plan_store.py`（新，复用 `review_shards.py` 的落盘范式：
   临时文件写入 → 用同一份校验逻辑重新读一遍 → `os.replace` 原子提交 → 失败清理临时文件；
   manifest + sha256，不覆盖旧文件，只加新版本）
   - 单位：每天一个 `DayPlan` 记录，按月分片（复用 `review_shards.py` 的分桶/manifest 思路，
     字段换成 `DayPlan` 而不是 `ReviewItem`）。
   - `write(day_plan)`：**提交前必须先跑 `check_invariants()`，不过 5 条护栏就拒绝写入**，
     错误路径要精确到具体是哪一条护栏（复用 `StorageError` 的 `path` 字段范式）。
   - `write(month_close)`：追加式记录，一旦写入不可覆盖（闭环是历史事实，不能被"改分"）。
   - `load(date)` / `load_month(year, month)`：只读查询。

3. `ky/__main__.py` 新增两个子命令（延续 `preflight`/`ledger` 已有的"读优先、写要显式"风格）：
   - `py -m ky snapshot --config ... --items ... --date ...`：只读，打印 `StateSnapshot`。
   - `py -m ky day-plan submit --config ... --plan <plan.yaml> --store <dir>`：
     读入 AI 生成的 `DayPlan`（YAML），跑 `check_invariants`，通过则原子落盘（exit 0），
     不通过则**不写任何东西**、打印精确到字段的违规原因（exit 2，与 `preflight` 的退出码
     约定一致）。
   - `py -m ky month-close --store <dir> --year --month`：读该月已落盘的 `DayPlan`，
     调用 `close_month`，打印结果；**首个版本只读打印，不自动落盘 `MonthClose`**——
     "闭环"是否要写入历史记录是一个需要用户明确同意的动作，不应该是查询命令的副作用
     （关闭月份 = 承诺"这个月的账定了"，理应是一次单独、显式的写命令，
     可以放到下一轮再加，这里先给最小可用的只读汇总）。

**对已有模块的最小改动（不算"新增"，是补齐决议里已经承诺、但代码没做的部分）**：
- `review_clip.py::select_daily_reviews()` 加一个可选的每日预算覆盖参数（见①的第六条发现）。
- `budget.py::allocate_new_content()` 的签名已经是"传入分钟数"，不需要改（决议表格里的 C5
  实测已经做到了，主控表格写的"已参数化，不写死 120"是准确的）。

**不新增**：不做排课 UI、不做"推荐值"函数、不做优化器、不碰 ③④⑤ 阶段的任何东西。

## ④ 缺口 5：系统 / AI 边界怎么划

**一句话边界**：**系统只回答"这份计划能不能被记账"，AI 回答"今天应该记什么账"。
系统提供的每一个函数要么是"读"（快照/查询），要么是"验证"（`check_invariants`
式的布尔判断+精确原因），要么是"写"（原子落盘一份已验证的记录）——**系统里不存在
第四类函数：不存在任何"建议/推荐/默认/优化"式的函数**。这条规则本身就是可机器检查的：
CI 可以对 `ky/schedule/`、`ky/storage/` 下的公开函数名做一次静态审计，
凡是函数名或返回字段命中 `recommend*`/`suggest*`/`default*`/`optimal*`/`next_month_*`
就判违规——`monthly_close.py` 已经有先例（`test_close_does_not_prescribe_next_month`
用 `hasattr` 断言这几个字段不存在），只需把这条测试模式复制到 `state_snapshot.py`
和 `day_plan_store.py` 上。

**具体划分表**：

| 归属 | 做什么 | 怎么被验证 |
|---|---|---|
| 系统 | 暴露"今天有什么"（快照）：各科剩余/已学、到期复习、backlog、词汇剩余、距考天数 | 快照是纯函数，同样输入必出同样输出（可回放测试） |
| 系统 | 定义 5 条不变量并强制执行：权重和=1、比例不倒置、单项上限、超载必须显式 backlog、不得为负 | `check_invariants` 已有 21 个回归测试锁死；新增字段必须新增对应测试 |
| 系统 | 原子落盘 AI 提交的计划，且**只有通过护栏才落盘** | `day_plan_store.write()` 拒绝路径的单测：违规输入 → 目录内容不变（用 `os.stat`/`hash` 断言无副作用文件） |
| 系统 | 诚实汇总月度实绩，不产出"下月该给多少"这类字段 | 复用 `test_close_does_not_prescribe_next_month` 的断言模式 |
| AI | 决定当日可用分钟数（`available_minutes`） | 系统不检查这个数"对不对"，只检查它 ≥0 且与它衍生的分配一致（护栏 5） |
| AI | 决定当日四科/词汇/长难句的分钟与词数分配 | 系统只检查"分配完整"（权重和=1、不倒置），不检查"分得像不像 40/20/40" |
| AI | 决定今天要不要处理 backlog、处理多少 | 系统只要求"超载必须显式声明"，不要求"必须清空"（决议已废止这条硬约束） |
| AI | 决定"前十几个月背单词、之后转长难句"的切换时机 | 系统不设置任何日期阈值；`phrase_minutes` 从 0 变为非 0 这件事本身对系统而言不是"事件"，只是又一个当天输入 |

**为什么这样划不会退化成"系统替你排课"**：系统里没有一个函数在给定快照后
能产出一个"这天该怎么分"的答案——`state_snapshot.py` 只读不算，
`check_invariants` 只做布尔判断不做数值生成，`day_plan_store` 只落盘不改内容。
即使把这三个模块全部串起来自动跑，输出也只是"记账系统"，不会产生一天的计划——
**计划这一步永远需要外部（AI）先给出一份具体数字，系统才有东西可验证/可存**。
这是一个结构性保证，不是靠"承诺不这么做"。

**为什么这样划不会让 24 个月的纵向结构散架**：结构感不是靠系统"管住"每一天，
而是靠**状态可见、账目诚实、历史不可篡改**这三件事的叠加——
下一个处理某天任务的 AI（哪怕是完全不同的一次对话）打开 `snapshot` 就能看到
"数学还剩 40% 没学、英语 backlog 堆了 300 分钟、还有 480 天"，这个可见性本身
就会约束它做出连贯的决定，跟人类学生自己看进度表决定今天学什么是一回事。
系统的角色是**保证这张进度表不撒谎**，不是替人（或替 AI）做决定。

## ⑤ 实施步骤与机器可验证的完成标准

**顺序按"读 → 验证 → 写 → 串 CLI"排列，每一步都可以独立跑测试，不需要等下一步**：

1. **状态快照模块**（`ky/schedule/state_snapshot.py`）
   完成标准：新增单测覆盖——(a) 给定构造好的知识树+复习队列，快照数字与手算一致；
   (b) 快照函数不产生任何文件系统写操作（可用 `tmp_path` 沙盒 + 断言目录内容不变来测）；
   (c) 每个知识树来源字段都带 `tree_status`，且当前三科真实数据跑出来全部标记非 approved
   （回归锁死"不能悄悄升级成覆盖率数据"这件事）。

2. **`review_clip.py` 补签名**（决口 6）
   完成标准：新增参数默认值下，已有 306 个测试**一个不改地全部继续通过**
   （纯加参数，不改默认行为）；新增测试证明传入覆盖值后硬上限/软配额确实按新值算，
   不传时行为与今天完全一致（字节级同输出）。

3. **`day_plan_store.py`**
   完成标准：(a) 违规 `DayPlan`（人为构造一个不过 `check_invariants` 的）提交后，
   目录内容与提交前的哈希完全一致（零副作用）；(b) 合法 `DayPlan` 提交后可原样读回
   （round-trip 相等）；(c) 连续提交同一天两次视为版本更新还是拒绝，需要在实现前
   明确选一个并写成测试（我倾向"同一天只能有一条记录，第二次提交是显式覆盖操作，
   需要 `--force`"，防止"改历史账"的误用，但这属于设计细节，需要用户或三方在方案
   阶段拍板，不在本报告里替用户决定）。

4. **CLI 三个子命令**
   完成标准：`snapshot`/`day-plan submit`/`month-close` 都遵守现有 `preflight` 的退出码
   约定（0=成功，2=契约/护栏违规，3=用法错误）；三个命令都有"违规输入不产生任何文件"
   的黑盒测试（起一个临时目录，跑 CLI 子进程，断言目录树不变）。

5. **回归总闸**
   完成标准：`py -3 -m unittest discover` 全绿，且新增测试数量 > 0
   （防止"代码加了但没测试锁住"）。

## ⑥ 明确不做

- 不做③④⑤阶段的任何东西（本机 Web 投影、课表协同、可视化）。
- 不做任何"推荐/建议/默认分配"函数——即使只是给用户看的提示文案也不做，
  防止"提示"事实上变成隐性排课。
- 不做长难句/短语素材的接入——决议已明确"留扩展位，当前不安排来源"，
  `phrase_minutes` 字段留着、值可以是 0，仅此而已。
- 不重写/替换 `review_clip.py` 的排序核（纪律第 2 条），只加一个可选参数。
- 不实现"完成后如何推进复习间隔"（SM2/FSRS 式 due_date 前移逻辑）——
  这是①阶段间隔复习引擎本身缺的一块（见①缺口4的深层发现），不是②的范围，
  但建议**单独立项**，因为它比②的月度闭环更基础：没有它，"复习完成"这件事
  永远无法反映到 `ReviewItem` 状态里，`review_clip.py` 的排序核会一直基于
  "从未完成过"的假设运行。
- 不自动把 `month-close` 的结果写成不可逆历史记录（见③的 CLI 设计），
  这一步涉及"什么时候算这个月定账了"这种业务判断，留给下一轮或用户显式拍板。
- 不处理"知识树 approved 之前能不能用于快照"这个悬而未决的政策问题
  （见①和⑦），本报告只做到"如实标注状态"，不越权替用户决定能不能用。

## 一句话总结

**②可以落地**；最小终态包含 **`state_snapshot.py`（只读快照）+ `day_plan_store.py`（护栏后原子落盘）+
`ky/__main__.py` 的 `snapshot`/`day-plan submit`/`month-close` 三个 CLI 子命令**，
外加对 `review_clip.py` 的一处**签名级**（非算法级）补丁；边界划法是
**系统只做"读快照、判护栏、原子写账"这三类零决策函数，凡是产生具体数值建议的函数一律禁止存在**，
AI 保留对每一个具体数字的完全裁量权，系统靠"状态可见+账目不可篡改"而不是"数值管控"来维持
24 个月的纵向结构。
