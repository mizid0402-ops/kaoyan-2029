## 二、架构 —— **定案：一个站点，写文件、重建投影、页面即时反映**

### 用户的**原意**（需求文档 §7.3 原文）

```
用户在网页上修改课程表
→ 网页将课程表保存到数据库
→ AI 生成周计划前读取最新课程表
→ AI 输出新计划并写回数据库
→ 前端页面自动刷新展示
```

**一个统一站点，改完在当前页面立刻看到结果。**

### 主控的一处误判（记录下来，避免再犯）

主控先提出"§7.1 第 7/8/9 条是写操作，与 ③ 的只读决定冲突"，并给出三个方案。
用户顺着那个框架答了"只读展示 + 另建一个可写的"。

**但用户随后澄清：那不是原意，原意是一个统一站点 + 页面即时反映。**
主控把"只读"当成了不可动的前提，再让用户的需求去迁就它——**这是框架先行导致的误导。**

### 冲突其实不成立：`--immutable` 只该约束"投影"，不该约束"整个应用"

| 对象 | 性质 | 可写性 |
|---|---|---|
| `data/course_schedule/*.yaml` 等 | **真相源** | ✅ **应用写它** |
| `data/projections/*.sqlite` | **派生读缓存**（可随时删了重建） | ❌ 保持 `--immutable` |

**两者不矛盾。** 正确做法：

```
① 用户在网页上改课表
② 应用写【课表文件】（不写投影）
③ 应用重建投影（已有命令：py -3.12 -m ky.projection，实测约一秒级）
④ 页面重新读投影 → 立刻显示新数据
```

**这样同时满足三件事**：
- **一个统一站点**（用户原意）
- **文件是真相源**（架构优势保留）
- **投影仍然只读**（③ 的验证结论不作废——`--immutable` 依然有效，
  只是它保护的是"缓存不被绕过真相源直接改"，而不是"应用不能写任何东西"）

### 由此确定的数据流

```
浏览器（一个站点）
   │  读：直接查投影（只读）
   │  写：POST 课表 → 应用写文件
   ↓
课表文件（真相源）
   ↓ 重建投影
projection.sqlite（派生缓存，--immutable）
   ↑ 读
浏览器重新加载 → 看到新数据
```

**关键约束（不能违反）**：
- 应用**永不直接改投影**——只改文件，然后重建
- 重建是**幂等且快速**的（已有实现，两次构建内容哈希相同）
- 因此"投影被改坏"这件事**结构上不可能发生**

### 仍需用户确认的两点

| # | 问题 | 为什么需要 |
|---|---|---|
| **W1** | 写入范围：**只做课表**，还是**也做"录入学习记录"**（§7.1 第 8 条）？ | 决定表单与落盘范围 |
| **W2** | 重建时机：**保存后自动重建**，还是手动跑命令？ | 影响"改完就能看到"这条体验 |

**主控建议**：W1 先只做课表（课表是排计划的前置输入，优先级最高）；
W2 **自动重建**（否则会出现"我改了课表怎么没变"的困惑，正是用户刚遇到的那类问题）。

## 五、顺带记录的缺口（用户实际遇到）

**`serve.py` 不打印访问地址、也不自动开浏览器。** 用户运行后屏幕上没有任何"点这里"的提示，
浏览器自然不会弹出。待办：加 `--open`（默认打开浏览器）或在启动时打印可点击的 URL。
