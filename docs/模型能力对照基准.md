# 模型能力对照基准（审查 vs 写码）

> 目的：用**可验证的产出**比较不同模型在「审查」与「写码」两个角色上的优劣，
> 而不是靠印象。所有结论必须能追溯到具体文件、具体命令输出、或具体的代码事实。
>
> 建立日期：2026-09-12

---

## 一、为什么"审查"和"写码"是不同的能力，而且可以同时被同一把尺子测

关键在于约束不同：

| | 写码 | 审查 |
|---|---|---|
| 任务性质 | **构造**：产出能跑、能维护的东西 | **搜索**：在不确定中找真缺陷 |
| 主要失败模式 | 功能不对、边界没处理、与既有风格冲突 | **漏报**（没找到）与**误报**（报了假的） |
| 关键指标 | 一次通过率、缺陷密度、约束遵守度 | **召回率** × 影响面、误报率、验证手段 |
| 容易被什么骗到 | 测试全绿（可能测试是空的） | 报告写得漂亮（可能全是风格意见） |

同一个模型带同样的 effort，不可能同时最优化这两端。所以"谁更强"是**分角色的**问题。
下面的基准把两个角色分开打分。

## 二、可验证的度量维度（每条都能从产物里抠出来）

### 审查角色

| 代号 | 度量 | 怎么算 |
|---|---|---|
| R1 | **发现数** | 报告中 BLOCKER/MAJOR/MINOR 计数（须有位置与触发条件） |
| R2 | **命中率** | 被后续验证坐实为真缺陷的比例 |
| R3 | **误报率** | 报了但不成立、或纯风格意见被包装成缺陷的比例 |
| R4 | **验证手段** | 是否做了**变异测试**（改坏实现→确认测试变红→还原+哈希）；只做静态阅读的记 0 |
| R5 | **自证的可复现性** | 每条发现是否给了可执行的复现命令/代码；给实测输出的加分 |
| R6 | **越界与自律** | 是否遵守"不改被测代码/审查方工具"的约束；变异后是否真还原（哈希核对） |
| R7 | **独有视角** | 是否找到前几轮**都没提到**的缺陷（而非重复既有结论） |

### 写码角色

| 代号 | 度量 | 怎么算 |
|---|---|---|
| W1 | **一次通过率** | 交付时自己的测试是否通过（且不是空真） |
| W2 | **缺陷密度** | 后续审查中被坐实的缺陷数 ÷ 交付代码行数（千行） |
| W3 | **约束遵守度** | 是否只改了被允许的文件；是否守住了已知的边界（如不改既有文件） |
| W4 | **诚实度** | "未解决"一节是否真实列出没做到的事；有无事后被证伪的过度承诺 |
| W5 | **既有风格一致性** | 是否沿用项目的错误路径风格、命名、测试组织方式 |
| W6 | **脆弱点自识别** | 是否主动指出自己方案最脆弱的一处，且该处后来确实出问题 |
| W7 | **实测而非声称** | 性能/规模类结论是否给了自己跑出来的数字（而非估算或复述他人） |

## 三、本次已获得的实验条件

不是人为设计的实验，而是实际工作顺序产生的组合，正好覆盖两个角色：

| 轮次 | 写码 | 审查 | 输入 | 关键产出 |
|---|---|---|---|---|
| 阶段 1 实现 | **claude-sonnet-5**（high） | — | 契约 | 49 条测试全绿 |
| 第 3 轮 | — | **gpt-5.6-sol**（high） | 阶段 1 代码 | 裁决 FAIL：4 个 MAJOR + 7 条假测试 |
| 第 3 轮补 | **claude-sonnet-5** | — | Codex 报告 | 修复 → 78 条测试全绿 |
| 第 3 轮重审 | — | **gpt-5.6-sol** | 修复后代码 | 变异测试：M1–M4 RESOLVED，6/6 变异被杀死；发现 B 项残留 |
| 第 3 轮终审 | — | **gpt-5.6-sol** | 再次修复 | 6,528 例扫描 0 失败 → **PASS** |
| 第 3 轮补 2 | （DSH 收尾） | **gpt-5.6-sol** | 我改的 3 文件 | 语义裁定：接受精确实现；发现"全称断言"被证伪 |
| 第 4 轮断链 | — | **gpt-5.6-sol** | 我关条件的改动 | **FAIL**：只关了一半 + 队列存储扩展性实测 |
| **第 5 轮（进行中）** | **gpt-5.6-luna**（high） | **claude-opus-5**（high） | 阶段 2 开工 / 同一份 round-4 | 并行，互不可见 |

**天然的对照**：`round-4-codex.md` 是一份**内容固定、结论明确（FAIL + 3 条最小修法）**的审查报告。
Opus 5 拿到的正是这份报告。因此可以测出：

- Opus 5 会不会**独立复核**它的技术主张（包括那个 `2**53 + 1` 反例），还是直接照做？
- 它能不能找出 round-4 **漏掉**的东西（R7）？
- 它对 D 节那个"是否该分片"的设计问题，给出同意、不同意还是更细的方案？

单条更新重写 435,807 B → 12,903 B（1,000 条时）。

**一个它没做到的点**：那个"规模测试"只断言 `[1000, 5000]` 这个列表本身，
没有任何性能或正确性上限——它能捕获崩溃，但**证明不了分片有收益**。

| 度量 | 值 | 依据 |
|---|---|---|
| R1 发现数 | 高 | 1 BLOCKER + 3 MAJOR + 1 MINOR，另加 4 条非阻塞限制 |

| R5 可复现性 | 强 | 每条给复现方式与实测输出 |
| R6 越界与自律 | 良好 | 变异后哈希逐位核对还原 |
| R7 独有视角 | **强** | 找到 Codex 五轮**都没看到**的两处：YAML 重复键静默丢弃（"last wins" 绕过 fail-closed）、`WEIGHT_TOLERANCE` 泄漏到比例字段产生 −1 分钟软配额 |

**它做的最有价值的一件事是反驳**：它**不同意** round-4 的 FAIL，理由是 round-4 据以 FAIL 的
唯一条件（M1）在其断言域内不可触发、至多算 MINOR；而真正够格 FAIL 的 BLOCKER-1 是 round-4
**没发现的**。它同时**反驳了 round-4 关于分片的首要理由**（见 5.3）。

### 5.3 DSH 对两个关键争议的独立裁决

**争议一：`2**53 + 1` 反例到底成不成立？**

- round-4 报：`total = 2**53 + 1 = 9007199254740993` 时精确值与旧 float 值不同。
- Opus 报：这个具体值**不**不同（两者都是 4053239664633446），且指出 round-4 自己文档里写的是另一个值。
- **DSH 实测**：Opus 对；且**第一个**出现分歧的预算是 `2**53 - 1 = 9007199254740991`，
  比两边说的都更早一位。三方在这一点上只有 Opus 的数字是对的。
  → 说明**反例的精确性本身也需要被复核**，不能因为结论方向对就放过数字。

**争议二：分片的首要理由是不是性能？**

- round-4 用一组耗时数据论证"20,000 条不适合每次全量解析"，据此主张阶段 2 前分片。
- Opus 反驳：那组数字里约 96% 是 **PyYAML 的纯 Python 解析器**，而本机 libyaml 可用却未启用。
- **DSH 实测**（同一文档，同机）：

  | 条目数 | 当前 SafeLoader | CSafeLoader | 加速 |
  |---:|---:|---:|---:|
  | 1,000 | 969 ms | 142 ms | 6.8× |
  | 5,000 | 5,106 ms | 1,168 ms | 4.4× |
  | 20,000 | 21,465 ms | 5,205 ms | **4.1×** |

  → **Opus 的反驳成立**。`yaml.__with_libyaml__ == True`，libyaml 本来就在，
  改一行加载器基类就能拿回 4 倍，不需要动架构。
  **性能这条理由基本失效**；分片真正还站得住的理由只剩两条：**审计哈希粒度**与**故障爆炸半径**。
  这直接改变了"阶段 2 前必须改分片"这个建议的紧迫性。

## 六、跨模型横向对照（同一把尺子）

### 6.1 审查角色

| 度量 | claude-sonnet-5 | gpt-5.6-sol | claude-opus-5 |
|---|---|---|---|
| 可评轮次 | 1（自审） | 5（他审） | 1（他审） |
| 发现数 | 6（A1–A6） | 4 MAJOR + 13 缺陷 + 7 假测试 | 1 BLOCKER + 3 MAJOR + 1 MINOR |
| 命中率 | 全部属实 | 全部属实 | 全部属实 |
| 误报率 | 低 | 低 | 低 |
| 变异测试 | 无 | **有（每轮，6/6 杀死）** | **有（8 项，7 杀死 + 1 证明不可达）** |
| 独有发现 | — | recovery 语义误用、单文件队列扩展性 | **YAML 重复键静默丢弃、tolerance 泄漏到比例字段** |
| 显著特点 | 覆盖面窄但在自己域内准 | **广度高，善用实测数字与变异** | **敢反驳上游结论，且能拆穿"看似充分的理由"** |

**结论**：三个模型在"找真缺陷"上都不产生误报，差别在**搜索方向**：
`gpt-5.6-sol` 倾向于**系统性反例搜索**（大量参数组合、变异矩阵）；
`claude-opus-5` 倾向于**攻击既有结论的依据**（复核上游前提、找被默认接受的假设）；
`claude-sonnet-5` 自审时倾向于**自己代码的可维护性与边界**，覆盖面明显更窄。

必须说清楚的一个**不公平之处**：sol 跑了 5 轮、累计 100 万+ token，
opus 只跑了 1 轮。**发现数不能直接横向比**，只能说"单轮内的产出质量"opus 更高。

## 七、可以下的结论（有证据支撑）

1. **"测试全绿"与"验收通过"在本项目里被反复证明是两件事。**
   49 条全绿 → 4 个 MAJOR；56 条全绿 → 同样的 4 个还在；88 条全绿 → M1 残留；
   102 条全绿 → 仍有 1 BLOCKER + 3 MAJOR 被 opus 挖出。四次没有一次是测试抓到的。

2. **审查的价值主要来自"搜索"，写码的价值主要来自"构造"，两者不是同一能力的强弱。**
   本项目至今所有高价值审查产出都是"找到别人没找的东西"：
   假的测试、没覆盖的边界、被默认接受的前提、看似充分其实不成立的理由。

3. **`claude-opus-5` 显示出一项前面模型没表现出的能力：拆穿论据。**
   它不只找代码缺陷，还去复核"上一轮凭什么这么判"。这次它同时做到了两件事：
   把上游的 FAIL 判轻（M1 至多 MINOR），又把上游漏掉的 BLOCKER 挖出来，
   并且用一个一行可修的意外（C 加载器）瓦解了上游主张架构改造的首要理由。

4. **`gpt-5.6-sol` 的横向广度仍然是最强的。**
   它五轮里累计找到的独有问题（`recovery_selection` 语义误用、`skill_graph` 门槛可复用、
   单文件队列扩展性）都是**跨模块、跨生命周期的**，需要真的去读别的模块才能发现。
   opus 这一轮更强的是纵深与反驳，不是广度。

5. **一个必须写进流程的教训：反例的精确性也要复核。**
   本轮三方对同一个反例给了三个不同的数字（`2**53+1`、`2**53+1`、以及正确的 `2**53-1`）。
   结论方向对，不代表引用的数字对。**数字必须现跑。**
